# 工作台上下文压缩验证记录

2026-11-15 在 `codex/project-conversation-agent` 上验证了 Project → Conversation → Run 工作台。起点为 `2ba0bfe`，实现和回归测试位于 `3ec3ee2`。[可重复执行的压缩回归用例](../backend/delveforge-infrastructure/src/test/java/com/ayywl/delveforge/infrastructure/workbench/ConversationCompactionTest.java)

## 模型每次收到哪些内容

SQLite 保存完整消息、工具协议、调用回执和已捕获输出。每段对话只有一份持久检查点，由 `summary`、`through_seq` 和 `context_version` 标识。发给模型的消息在请求前组装，包含系统指令、工具定义、当前检查点、选中的已覆盖用户原文及未覆盖的近期记录。

已覆盖的用户原文在整段对话内从新往旧选取。SQLite 每页读 32 条，使用所配置的分词器核算完整消息的边际用量。遇到下一条放不下时停止，已选消息以用户角色按时间顺序发送，保留最近一条省略原文的记录号。这样较老的要求不会越过一条未重放的修正重新出现。尾部消息只发送一次。尚未得到助手回应的连续用户输入全部保留。如果这部分连同系统指令和工具已经超限，Run 在发送前暂停。

每条独立用户消息、普通助手回复或完整工具批次构成一个切分单位。同一批次的助手消息、所有调用 ID 及对应的全部回执共同移动。保留的消息沿用原顺序、参数和思考字段。缺失、重复或孤立的回执会使 Run 暂停。切换思考模式后，若旧助手消息缺少当前适配器需要的推理字段，工作台按整批引用旧记录，继续保留兼容的近期批次。

## 预算与发布条件

设硬上限为 `usableInputTokens()`，软阈值为 `triggerTokens()`。工作台目标取 `targetTokens()` 与软阈值的 5/6 中较小者。这个上限让低阈值实验也有可测的余量。系统指令、工具描述、Schema 和实际保留的推理都计入决策输入。

| 项目 | 默认配置 | 长对话回归配置 |
| --- | ---: | ---: |
| 窗口 / 输出预留 | 1,000,000 / 65,536 | 9,200 / 1,200 |
| 可用输入 / 压缩阈值 | 934,464 / 841,018 | 8,000 / 6,400 |
| 压缩后目标 | 700,848 | 5,333 |
| 已覆盖用户原文上限 | 4,096 | 1,333 |
| 近期完整记录的初始预算上限 | 350,424 | 2,666 |

已覆盖原文最多占目标的 1/4，并封顶于 4,096 tokens，使长期任务的重放成本有固定上限。近期记录先分配至多目标的 1/2，实际固定提示与原文预留占用较多时再收紧。检查点和最新输入优先。原文及近期记录的具体条数随内容而变。[保留参数与切分规则](../backend/delveforge-application/src/main/java/com/ayywl/delveforge/application/workbench/ConversationRetention.java)

摘要请求单独计数，且不带工具。前缀放不下时，在完整批次边界上缩短前缀，因此决策尾部会变长。发送摘要前先测最小重建提示，拿到回复后再测包括新摘要、原文、尾部和工具在内的完整决策提示。通常只发布达到目标的检查点。原提示已经超过硬上限时，也可发布回到硬上限内、且至少减少「软阈值减目标」的结果。该结果可直接用于下一次决策。

## 检查点、失败与并发

新检查点由「上一检查点 + 新覆盖前缀」生成。三个栏目分别是用户要求、执行证据、待办与未知。摘要指令要求区分仍有效和已被取代的要求、助手推测与工具观察，保留精确的路径、标志、参数、验收键、已运行测试和输出缺口。

`[#N]` 中的 N 来自 `record.seq`。新摘要须至少引用一个新覆盖的真实记录号。沿用旧引用时，检查它是否来自给定的上一检查点或其边界，且在本对话中存在。助手可用 `df-workbench history N` 分页查到原文。原来保存的纯文本摘要仍可读取，新写入使用三个栏目。

发布时按预期 `context_version` 和递增的 `through_seq` 条件更新。版本竞争失败会从最新状态重建。本次压缩期间接收的输入留在冻结边界外。普通决策和工具准入继续检查新输入。

- 摘要截断、提供方报错、结构或来源无效、压缩量过小时，沿用仍符合硬上限的原提示。同一前台 Run 不为同一失败前缀反复请求摘要。发生足够的新增长或跨过硬上限时，新的前缀可以再试。暂缓记录位于内存，控制端重启后可以重新尝试。实际网络发送沿用适配器的重试与累计额度。
- 已超过硬上限时，临时视图保留已有检查点、已选用户原文、全部尚未进入检查点的用户原文，以及能够完整放入的近期批次。省略的执行记录给出可查编号。临时视图不更新覆盖位置或版本。必要内容仍放不下时，Run 暂停并保存原因。调大窗口后可继续同一个 Run。

## 历史复演与实测

使用项目内置的 DeepSeek V4.1 Flash 分词器和 HIGH 思考模板。历史复演只读打开稳定性实验的 SQLite，取最终答复生成前的记录，在同一套系统指令和工具下分别计算完整历史与已保存检查点重建出的输入。两行数据都是本地模板计数。复演的模型请求数为 0。

| 历史现场 | 完整历史 → 检查点视图 | 已覆盖用户原文 | 尾部完整记录 | 检查点覆盖至 |
| --- | ---: | ---: | ---: | ---: |
| C2 | 8,632 → 4,466 | 3 条，301 tokens | 6 条，2,945 tokens | 189 |
| C4 | 52,479 → 5,230 | 3 条，289 tokens | 7 条，3,570 tokens | 273 |

C2 的 JSON 修正在记录 184。两份历史检查点都没写出字面量 `--format json`，重建后的用户消息均保留该标志和 `reader`、`open`、`overdue` 三个键，所有工具回执可配对。C2 当时的 CLI 验收确实失败。C4 原实验花费 41 次请求，其中 14 次用于摘要。本次只复演上下文。

另一个可重复的夹具用独立 SQLite 跨两个 Run 追加 53 条原始用户消息。每次真实组装并计数决策提示，由确定性模型替身返回故意漏掉 JSON 契约的摘要。下表来自全量验证中的这组测试。临时项目 UUID 的分词可使含系统指令的总数有少量变化。

| 压缩轮次 | 原提示 → 新提示 | 已覆盖用户原文 | 完整尾部 tokens | 摘要输入 tokens | 累计摘要请求 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 11,118 → 4,837 | 17 条，995 tokens | 2,874 | 7,090 | 1 |
| 2 | 12,727 → 5,173 | 24 条，1,331 tokens | 2,874 | 7,621 | 2 |
| 3 | 13,043 → 5,168 | 23 条，1,326 tokens | 2,874 | 7,594 | 3 |

三轮的 JSON 修正都已进入压缩前缀，在新提示中仍以用户身份出现。每次摘要输入均在 8,000 以内，新决策提示均在 5,333 以内。实际尾部比初始预算多 208 tokens，是为了让摘要输入也放得下。默认百万窗口的独立夹具中，111 条已覆盖用户消息实际保留 47 条，占 4,089 tokens。

**语义边界。** 回归故意让摘要漏掉超长原文中的档案格式 `LGR-7Z`。当这条原文也超出重放预算时，最终提示确实没有该细节。测试用处于已准入状态的工具凭据，按真实记录号分页取回了完整原文并逐字比对。结构、来源和预算可以验证，模型能否保留每一项语义、是否会主动回查仍取决于它的判断。
