# V2 — Precision Room

2026-10-31 · Operate / Read · 本地审阅候选

V1 因审美与结构质量被产品负责人拒绝。测试通过不改变这个结论；V1 是反例与比较点，不是 V2 的视觉权威。

## 设计输入

开发者需要在长时间本地工作中确认「我在哪个项目、下一步是什么、代码究竟处于什么可信状态」。数据对象是保存的项目、带 revision 的画像、仓库分析快照、候选方向、有序 Step、Agent Run、冻结 Candidate 和正式 Delivery。少量对象如实显示，不补统计、日期或完成率。原 API、确认与授权边界是行为来源。

Taste App Screen 的实际探索命令使用 `--app --kind devtools --screens overview,list,detail,builder --keep palette,type --options 3 --seed 31102`，给出 framed-sheet、achromatic-ledger、data-terminal。再运行 framed-sheet 的完整 sheet。取其明确边界、少量色彩和内容决定布局的原则；根据用户偏好把 frame 改为石墨顶栏和浅灰蓝导航，把运行活动限定为深色区域。没有把 library 示例中的部署、健康指标或图表带入产品。

这些是浏览器渲染的设计探索，使用同一组合成内容，明确标注「非已实现产品截图」。每种均有 1440 和 420 两个尺寸。

| 方向 | 导航 / 空间 | 字体与密度 | 工作面 / 手机 | 判断 |
|---|---|---|---|---|
| [精密控制室](concepts/precision.html) | 横向产品框架 + 有文字的阶段导航 + 独立项目卡 | 紧凑 Segoe UI，代码单独等宽；标题 25px | 窄配置区配大活动区；手机按当前任务顺序线性阅读 | 选定。阶段多且身份重要；可以容纳长证据与真实执行控制 |
| [模块化工作室](concepts/studio.html) | 水平项目条与导航，内容居中 | 较宽松 Calibri 界面，28px 轻标题 | 平衡的可组合模块，手机逐模块堆叠 | 项目入口友好，但配置与活动趋于同权，不利于运行中判断 |
| [技术案卷](concepts/dossier.html) | 无侧栏，页内阶段标签与宽阅读栏 | 衬线文档标题 + 无衬线正文，弱容器与规则线 | 宽技术文档配操作边栏，手机顺序成文 | 长证据阅读优良，但项目与阶段身份持续性弱，执行感不足 |

选型没有请求额外批准：用户已明确授权自主选择。没有图像生成、付费模型、钩子或新的产品规格初始化。

## 选定方向与每屏问题

识别要素是「有持久身份的项目卡」和「Run → Frozen Candidate → Formal Delivery 三个真实边界」，而不是颜色。屏幕去掉品牌色仍有不同的组成：

| 画面 | 先回答的问题 | V2 结构变化 |
|---|---|---|
| Shell | 正在操作哪个项目？ | 石墨横向产品栏、项目卡、分组阶段导航；手机折叠菜单，页面保留项目名 |
| 项目 | 继续哪个已保存流程？ | 原横向表格式行变成项目对象；身份、目标、真实交付数、当前阶段和继续操作各成组，新建入口独立 |
| Discovery | 对话形成了怎样的需求？ | 交互式左右气泡 + revision 笔记；真实等待时有三点反馈，充分性与审阅动作在笔记顶部 |
| 仓库 | 这个固定快照能复用什么？ | 仓库身份/完整路径和 revision 双栏题头，横向分区导航，宽技术阅读区；登记授权分开 |
| 方向 | 当前查看的方案为什么值得选择？ | 横向候选比较，问题→目标→适配与差异的主简报，风险/依据侧栏，独立决定区 |
| 规划 | 下一步允许改什么，前提是什么？ | 现状→目标与副本准备并排，连接时间线在对应步骤内展开范围与前提；重新规划是计划内工具 |
| 运行 | 当前发生什么，我能如何停止？ | 活动与停止控制先于配置；深色真实事件区，运行历史改为可展开索引 |
| Candidate / Delivery | 哪些代码被冻结/接受，测试了什么？ | 顶部摘要保留状态与入口，执行事件之后统一显示冻结文件、检查与交付；NOT_TESTED 保持原意 |

## Impeccable 如何改变实现

实际使用安装的 `impeccable.cmd context --target frontend/src/App.vue`，读取 shape/new-work/layout/typeset/distill/polish/adapt/harden/audit/critique 与 craft-floor。按照已提供的完整 brief 工作，跳过采访与额外概念确认。没有执行 init 或启用自动 hook。

- shape/layout：先确定每屏的问题与拓扑，再改模板；没有从 identity.css 换色开始。
- typeset：正文、标签、代码身份分工，代码路径不截断；侧栏英文最小 11px，并按真实背景校验对比度。
- distill：取消空运行历史轨道，时间纳入技术详情；保留停止含义、费用说明、失败和所有证据。
- adapt/harden：900px 导航折叠，手机显示项目身份；所有 Run 先看事件与停止，结果在底部且可直接跳转，完整长路径、25 条 Evidence 分页与空/失败状态测试。
- critique/audit/polish：两位独立评估者隔离审查后合并结果，实质修正见 [CRITIQUE.md](CRITIQUE.md)。源 detector 的空结果仅是机械检查。

质量判断是结构、内容和可用性。没有用 detector 得分替代产品负责人的视觉验收。

## 产品负责人反馈后的最终取舍

最初探索把对话处理成平铺记录、规划处理成索引/详情，并依独立评估把终态文件移到活动之前。
产品负责人随后明确指出这三点不如原有交互。最终采用熟悉的对话气泡、真实请求的思考动效、
有顺序连接的演化时间线，并在所有执行状态保持「事件在前、代码变更在底部」。
这些是对任务语境和用户偏好的修正，保留 V2 的整体框架、项目身份与其它页面结构，不追求每处都新奇。
