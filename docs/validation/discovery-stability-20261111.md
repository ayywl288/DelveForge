## 用户现在经历的流程

用户可以正常描述经验、说明不知道投入时间、放下原项目，再批准新的目标建议。
已有能力、历史 Evidence 和已接受消息继续保留。未知时间不被推断成“没有约束”或具体时长，
也不再要求约束区非空才能审阅；目标、技术基础、用户依据及实际语义充分性检查仍然保留。

“接受更新并继续”先完成批准，再恢复原问题，或用另一个请求身份请 AI 提问。
“仅接受更新”完全不生成。后续提问失败时，就近显示“画像已接受并保存”和后续结果，
提供明确的查询或提问入口，不要求用户发送“继续”“嗯”等填充消息。
待答问题始终可见，可以直接回答，也可以显式跳过这问、换个话题。

确认失败的消息保留原文，点击“编辑并重新发送”只取回文本，不立即调用 AI；用户发送时使用新身份。
未知结果保留原身份，仅查询或显式取消，不能直接再发。刷新后恢复服务端消息及待批提案，
本地失败原文放在原发送时间附近，不遮住后来已接受的回复。成功核对清除过期错误提示。

## 诊断依据与修复边界

检查了当前代码、原验收记录、应用安全日志及 `logs/delveforge.log.2026-11-10.0.gz`。
该归档在 23:58:43、23:58:54 的 8080 请求显示提取阶段 `UserProfileProposalParser.section` 失败，
对应完整分区数组结构校验。没有保留原始模型正文，不能据此确定具体字段或重建原始失败输入。
归档中 18290 端口的较早受控失败记录没有被当成真实用户本次故障的证明。

本轮可复现的问题还包括：规划对可选字段自洽性过度依赖模型，导致额外修正调用甚至丢弃有效回应；
约束区硬门槛促成数值追问；批准之后缺少衔接操作；失败原文只存在页面内存，刷新后不可编辑。
这些结论来自代码和新回归用例，未把一个最终堆栈位置当作全部根因。

对已完成但真正不可读的输出仍明确失败，不将非数组分区、空白、截断 JSON 或非法领域内容伪装成成功。
恢复依靠原请求终态及保留原文，不通过放宽事实结构、忽略提取失败或自动重发来掩盖错误。

## Application 决定流程，模型提供语义和正文

| 情况 | 接受行为 |
| --- | --- |
| nextAction 与可用 nextQuestion 不一致 | 根据服务器问题状态及可用问题决定 ASK / KEEP_PENDING / PAUSE，不额外请求模型。 |
| questionArea 缺失或枚举值不可用 | 有界有效问题归入 exploration；仍须通过历史重复和待答冲突检查。 |
| 可选问题重复、超长或落在已跳过维度 | 丢弃问题，保留有效回应，不制造新的 ASKED。 |
| 有真实未答问题，但模型缺失/误填上一问状态 | 保留 ASKED，丢弃竞争问题；不制造回答或拒绝。 |
| 有待批画像建议 | 固定 PAUSE，无新问题或首次邀请；保留对纠正/转向的自然回应。 |
| 模型的充分性与当前版本已保存结论冲突 | 使用已保存判断；确定性最低缺口仍独立执行。 |
| 模型自发给出 reviewInvitation | 无权生效；邀请仅由应用按充分性、未答问题与周期记录决定。 |
| 独立“不知道”“暂时不确定”等答复 | 不做事实提取，不产生 Evidence/revision；搁置原问，不记作维度拒答，并抑制同维度追问。 |
| 用户点击跳过/换题 | QUESTION 携带默认 false 的 replacePendingQuestion=true，明确纳入指纹；成功时原子替换，失败保留原问。 |

复杂意图与不确定表达的语义理解仍由现有模型负责，没有新增语义服务、LLM 组件或 Agent 框架。
JSON 根对象、必要字段类型、回复/数组长度及领域内容校验保留。已完成空白/损坏输出不做隐式修正重试，
传输结果未知更不自动重发。普通输入仍先提取、再 Thinking Low 规划；提取关闭思考，Coding Agent 配置不变。

提取的 hasNewFacts 现在仅为可选提示。实际完整分区差异决定是否变化；实际变化必须具有本轮依据，
没有实际变化不制造 Evidence 或 revision。精确前缀自动追加、人工保护、整轮待批、旧事实禁止未经批准恢复
均沿用上一轮策略，没有恢复 replacements、字符串授权、逐项 Patch 或历史 Evidence 下标撤回。

## 持久化、批准与恢复

沿用 V30 和所有历史迁移，没有新迁移。每份画像最多一个 PENDING 请求、一个待批提案和一个 ASKED。
模型调用不持有数据库事务，最终画像、Evidence、问题、邀请、对话及请求结果仍在同一短事务提交。
失败回滚和乐观版本/项目关联检查没有绕过。

批准仍只接受服务器快照，幂等返回原终态。增加只读
`GET /api/user-profiles/{id}/profile-updates/{proposalId}?projectId=...`，用于批准响应丢失后的精确核对。
后续生成是独立 QUESTION，独立身份、独立失败；不在批准事务内调用模型。

HTTP 502 本身不被视作未提交证明。客户端先查询原 discovery-request：COMPLETED 恢复接受结果，
FAILED / INTERRUPTED / CANCELLED 才允许取回编辑；PENDING / NOT_FOUND / 查询失败保留身份。
显式取消沿用迟到提交屏障。成功恢复不重复消息、不重复写画像，也不额外调用 Provider。

原请求身份继续存 localStorage，原文只在当前标签页 sessionStorage 有界保留：最多五份画像，
每份四条未接受尝试和一份12000字符输入草稿。尝试超过一天清除，草稿闲置一天过期；
只读加载不延长未改变草稿的期限。关闭会话、到期或超过数量后，本地原文可能不再可恢复。
本地原文始终显示为失败/待核对，不进入已接受服务器消息或模型历史。

新增固定诊断类别区分 PROFILE_EXTRACTION / DIALOGUE_PLANNING、TRANSPORT / HTTP /
EMPTY_OUTPUT / INCOMPLETE_OUTPUT / INVALID_OUTPUT / OUTPUT_LIMIT，提交冲突单独分类。
关联日志仅记录验证过的请求身份及固定字段，不记录用户原文、模型全文、凭据或仓库内容。

## 有界真实 DeepSeek 评估（待授权）

确定性和本地浏览器证据不能证明真实模型的措辞、语义分类与输出合规率。真实 Provider UX 结论为 **PENDING**。
建议后续授权上限为12次 Provider 请求，每次最多2048输出 token、最多12000输入 token，
